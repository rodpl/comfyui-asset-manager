# Story 1.1: Outputs Backend Hardening

## Status
Approved

## Story
**As a** ComfyUI user,
**I want** backend outputs APIs to behave reliably under typical usage conditions,
**so that** I can trust workflow actions and gallery data during daily use.

## Acceptance Criteria
1. API responses handle empty directories, malformed metadata, and expected gallery sizes without 500 errors; logging covers failure modes from simplified output gallery spec.
2. Workflow actions (load, open, show folder, copy path) return success/failure payloads with actionable messages and cover OS-specific cases.
3. Standard logging provides actionable summaries for workflow action outcomes without introducing new telemetry systems.

## Tasks / Subtasks
- [ ] Harden output scanning and enrichment to tolerate empty directories, malformed metadata, and large gallery scans while preserving existing response formats (AC: 1, 3). [Source: docs/architecture/if-enhancement-prd-provided-impact-analysis.md#files-that-will-need-modification]
  - [ ] Review `FilesystemOutputAdapter` and `ComfyUIOutputAdapter` behaviours so failed file reads or metadata parsing fall back without raising unhandled exceptions, logging failures through `src/utils/logger.py`. [Source: docs/architecture/technical-debt-and-known-issues.md#workarounds-and-gotchas]
  - [ ] Verify `OutputService` caching and sorting pathways handle empty results and large galleries without thrashing or returning stale metadata, aligning with `/asset_manager` contracts. [Source: docs/architecture/data-models-and-apis.md#api-specifications]
- [ ] Ensure `/asset_manager/outputs*` endpoints return structured success/error payloads for all filters and enrichment paths (AC: 1). [Source: docs/architecture/integration-points-and-external-dependencies.md#internal-integration-points]
  - [ ] Add defensive handling for invalid query parameters (dates, formats) and thumbs/file streaming errors so clients receive validation or not-found responses instead of 500s. [Source: docs/prd/technical-constraints-and-integration-requirements.md#integration-approach]
  - [ ] Update or add pytest coverage for API handlers covering empty directory, malformed metadata, and large directory scenarios to guard against regressions. [Source: docs/architecture/testing-reality.md#running-tests]
- [ ] Standardise workflow action outcomes (`load-workflow`, `open-system`, `show-folder`, copy path fallback) with actionable messaging and logging across supported OSs (AC: 2, 3). [Source: docs/prd/technical-constraints-and-integration-requirements.md#existing-technology-stack]
  - [ ] Confirm platform-specific shell invocations surface deterministic success/failure responses and log failures without new telemetry systems. [Source: docs/architecture/appendix-useful-commands-and-scripts.md#debugging-and-troubleshooting]
  - [ ] Extend automated tests (pytest and/or Playwright mocks) to validate success and error payloads for these workflow actions, including copy-path fallbacks when ComfyUI APIs are unavailable. [Source: docs/architecture/testing-reality.md#current-test-coverage]

## Dev Notes

### Previous Story Insights
- No earlier stories in Epic 1 have been completed; this draft establishes the first backend-focused deliverable for the Outputs-first release.

### Data Models
- `Output` entities store filename, dimensions, filesystem paths, and workflow metadata, enabling enrichment and filtering when serving gallery data. [Source: docs/architecture/data-models-and-apis.md#data-models]

### API Specifications
- `/asset_manager/outputs` and related endpoints are exposed through the `WebAPIAdapter`, providing listing, detail, refresh, file streaming, and workflow action capabilities for frontend consumers. [Source: docs/architecture/data-models-and-apis.md#api-specifications]

### File Locations
- Backend logic for this story sits under `src/domain/services/output_service.py` and `src/adapters/driven/comfyui_output_adapter.py`, with HTTP handling in `src/adapters/driving/web_api_adapter.py`. [Source: docs/architecture/source-tree-and-module-organization.md#key-modules-and-their-purpose]

### Logging & Diagnostics
- Reuse the project-wide logger defined in `src/utils/logger.py`, ensuring new diagnostics respect existing `LOG_LEVEL`/`DEBUG` controls instead of adding telemetry systems. [Source: docs/architecture/appendix-useful-commands-and-scripts.md#debugging-and-troubleshooting]
- Planned refinements for Outputs must rely on standard logging while deferring telemetry additions per release scope. [Source: docs/architecture/if-enhancement-prd-provided-impact-analysis.md#integration-considerations]

### Technical Constraints & Risks
- Maintain compatibility with the current filesystem-backed storage, OS-level shell operations, and `/asset_manager` API contracts to avoid breaking PromptServer integrations. [Source: docs/prd/technical-constraints-and-integration-requirements.md#existing-technology-stack]
- Outstanding spec backlog items (Outputs tasks #7–8) highlight pending performance and QA work that should remain visible after backend hardening. [Source: docs/architecture/technical-debt-and-known-issues.md#critical-technical-debt]

### Integration Touchpoints
- Frontend consumers rely on `ui/src/services/api.ts` to call Outputs endpoints, and backend adapters bridge to the filesystem and ComfyUI runtime; hardening must preserve these integrations. [Source: docs/architecture/integration-points-and-external-dependencies.md#internal-integration-points]

### Known Limitations & Fallbacks
- Some outputs lack workflow JSON sidecars; APIs must continue to return graceful fallbacks and log failures instead of raising errors. [Source: docs/architecture/technical-debt-and-known-issues.md#workarounds-and-gotchas]

### Testing
- Use the existing pytest suites under `tests/` to validate backend behaviour and ensure coverage remains above the enforced 70% threshold; invoke `poetry run pytest` for regression. [Source: docs/architecture/testing-reality.md#running-tests]
- Coordinate with frontend test suites (Vitest, Playwright) if workflow action payload changes impact UI expectations. [Source: docs/architecture/testing-reality.md#current-test-coverage]

## Project Structure Notes
- Planned changes remain within the established backend hierarchy (`src/domain/services`, `src/adapters/driving`, `src/adapters/driven`), aligning with the documented project structure and avoiding new module creation. [Source: docs/architecture/source-tree-and-module-organization.md#project-structure-actual]
